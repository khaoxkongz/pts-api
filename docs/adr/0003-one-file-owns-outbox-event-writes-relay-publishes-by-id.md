# One file owns Outbox Event writes; a relay retries by publishing by id

ADR-0002 left the Outbox Event lifecycle split. The dispatcher created the Outbox Event, and `NotificationDelivery` locked it and recorded it as published or failed, next to saving notifications. Nothing retried an Outbox Event: the dispatcher's one immediate publish was its only attempt, so a failed event, or one whose process died before or during publishing, was never notified. We decided on a relay that retries Outbox Events, and we split the code by what each part touches. Every write to an Outbox Event (create, lock, mark published, mark failed) and the query for due ones live in one Mongo outbox file. Lock, status and find-due sit behind an `OutboxEvents` interface. What is left of `NotificationDelivery` becomes `NotificationStore`, which only saves notifications. The relay finds due Outbox Events and calls the existing publish-by-id for each, so there is one lock, publish and mark sequence and every attempt goes through it.

## Considered Options

- **(a) Leave the split as it is**: rejected because the relay needs a find-due query and a lease. Under the old split these would land next to the notification writes, inside an interface whose name hides the Outbox half.
- **(b) An Outbox module whose interface covers create as well**: rejected because create has one implementation, and the dispatcher's payload tests already work well with `vi.mock` on the models. A fake added only to replace `vi.mock` is the hypothetical seam ADR-0002 warns against. Create stays a plain function in the outbox file.
- **(c) Move lock and status to the dispatcher's side**: rejected because publishing would lose its lifecycle tests, and the relay would either repeat the lock, publish and mark sequence or have to go through the dispatcher.
- **The relay locks and sets status itself, then hands publishing the payload**: rejected because it writes the lock, publish and mark sequence twice (immediate publish and relay), so the lease, the attempts count and error recording would have to be kept identical in two places.
- **Embed the Outbox Event in the planner document so it is saved atomically with the change**: rejected because every planner write in six modules would have to carry the event, to close a window one write wide.

## Consequences

- `OutboxEvents` has two implementations: the Mongo adapter and an in-memory fake in the publishing tests. Find-due belongs on it because the fake lets one in-memory store check find-due, lock and status together, which is how the relay is tested. The Mongo query filters themselves (lease, attempts cap, status) are not covered by unit tests, the same as the lock query before this decision.
- **Best effort, not atomic.** The change and its Outbox Event are separate writes, because the database runs as a standalone server and so rejects multi-document transactions. A crash between the two loses that Workflow Event's notifications. The upgrade path, if that ever matters, is to run the database as a replica set (one node is enough), have callers pass a session, and start the immediate publish after the commit rather than in a microtask.
- **The `session` option on dispatching is removed.** No caller passed it. With it, the immediate publish would run before the commit, find nothing to lock and leave the event pending. It comes back only with the replica-set upgrade above.
- **Immediate publish stays; the relay is the safety net.** The dispatcher still publishes straight away, so Live Push is not delayed by the relay's interval. The lock keeps the two from publishing the same event twice.
- **A lock is a lease.** An Outbox Event stuck processing can be locked again once its lease runs out. Saving notifications is idempotent per (event, account, Recipient Kind), so a lease that runs out while publishing is still going costs at most a repeated Live Push, which Live Push already allows.
- **Retries are capped.** Find-due skips an Outbox Event once its attempts reach a configured cap. An attempt is counted when the event is locked, so a publish that kills the process still counts. The event stays as its last attempt left it: failed with its last error, or processing if that attempt died. There is no separate dead-letter status.
- **The AuditLog stays with the dispatcher.** It records the Workflow Event itself, Audit-only ones included, not the pending notification.
- **The relay runs in process.** Like the participant reject sweep, it uses an interval timer that skips a tick while the previous one is still running, configured from `env` and started and stopped from `main.ts`. Several API instances can each run one, because the lock decides which of them publishes an event.
